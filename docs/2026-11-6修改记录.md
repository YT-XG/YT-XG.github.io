**反应机制设计要点：**

- 青金石：`reactSpeed 520` / `reactDist 320` / `holdDist 560`——敌方高速（含被减速的实际速度）进入 560 时先留着技能，进 320 立刻开盾。
- 长矛：`reactSpeed 600` / `reactDist 380` / `holdDist 560`——被高速逼近时保留突刺，进入 380 反刺。
- 红石：`reactSpeed 0`（关闭）——脉冲是进攻技，对冲高速敌人会硬吃长矛的高倍率伤害，模拟显示收益为负。
- `holdDist` 只影响"什么时候放"，**不产生任何转向/加速**，红线（AGENTS §3.2）仍成立。

### 40.4 结论

1. **对位层面已没有明显偏强的一方**：200 局稳健值为红青 49.0% / 长矛 51.0%，接近五五开；必需的 50 局/方向抽样为 42.0% / 58.0%，长矛略优但仍在种子波动范围内。
2. **穿透免伤的修正生效**：红石狂暴从「不可被击杀」变为可被长矛打到，强制分支胜率 100% → 46.7%/53.3%，结束时 HP 约 46–50（不再恒为 200）。
3. **青金石狂暴仍偏强**：护盾 50 → 25 后，满血强制分支仍有 86.7% 胜率，结束时约 94–99 HP；自然局翻盘率 56.9%–61.1%。
4. **红石狂暴偏弱**：自然局翻盘率仅 25.0%–37.5%，因为幸存红石通常在约 100 HP 进入狂暴，只能靠炸弹输出，长矛冲刺可将其击杀。
5. **突刺距离的边际效果很小**：0.40 → 0.42 只把 200 局胜率从 47.5/52.5 拉到 49.0/51.0；真正的对位改善来自穿透伤害修正与护盾削弱。继续加长会快速翻转（0.43s ≈ 60%、0.50s ≈ 69% 长矛胜率），因此停在 0.42s / 370px。

### 40.5 待确认

- 是否继续削弱青金石狂暴（例如护盾刷新间隔或 `dmgPerSec`），以及是否加强红石狂暴（炸弹伤害/频率或让红石在狂暴中也能造成撞击伤害）。
- 若希望长矛突刺距离更明显，需要接受长矛胜率升到 60% 以上。

## 49. 单文件拆分为 css/ + js/（12 个经典脚本）（同日第 49 次）

### 49.1 为什么拆

用户问："之后可能加十几二十几个物品，都写在一个 html 里是不是不太规范？"

结论拆成两半：

| 维度 | 判断 |
|---|---|
| **运行性能** | **无影响**。浏览器解析 250KB 单文件 vs 12 个文件，差异在毫秒级；多文件也只多 11 次本地读取（`file://` 无网络开销） |
| **AI / 人的编辑效率** | **有影响，而且是主因**。2536 行里改一个物品要读大段上下文；`TYPES` 已占 272 行（5 个物品，约 54 行/个），20 个物品将达 ~1100 行 |

所以按 **A 方案（经典 script 拆分）** 执行：能分文件、但**不引入构建、不改 ES Modules**。

> ⚠️ 关键约束：`type="module"` 在 `file://` 下会被 CORS 拦截，一旦改成 ES Modules 就**不能双击打开**了。因此全部用经典 `<script src>` + 共享顶层作用域。

## 57. 结算横幅不再压暗侧边排行 + canvas 按屏幕像素渲染（同日第 57 次）

### 57.1 需求原文

> 这个时候看不清左右伤害排行，另外字体也模糊

（截图：对局结束、中间弹出「蓝方 · 长矛 + 红石块 + 青金石块 + 冰块 胜利」，两侧排行被压暗到几乎读不出）

### 57.2 原因

| 现象 | 原因 |
|---|---|
| 结算时看不清排行 | `.banner` 是全屏 `inset:0` 的暗色蒙层（`rgba(8,10,15,.58→.86)`），盖住了整个舞台，而排行条是画在 canvas 上的，所以一起被压暗 |
| 字体模糊 | canvas 逻辑分辨率固定 1290×600，但 CSS 会把它放大到 1500~1700px；后备存储仍是 1290，浏览器等于把整张位图拉伸，字必然糊 |

### 57.3 改动清单

| # | 文件 | 类型 | 改动内容 |
|---|---|---|---|
| 1 | `js/00-base.js` | 修改 | 新增 `fitCanvas()`：`cv.width/height = 显示尺寸 × DPR`，随后 `ctx.setTransform(缩放)`；`W/H` 固定为逻辑 1290/600；`resize` 时重新适配 |
| 2 | `css/style.css` | 修改 | `.banner` 背景由整屏暗色改为**只在正中**的椭圆暗池（`ellipse 40% 30%`，78% 处透明）；`strong/em` 加 `text-shadow` 保证压在场地上也能读 |

### 57.4 实现要点

- 现在 **1 个 canvas 像素 = 1 个设备像素**：`backing = css 尺寸 × devicePixelRatio`，`ctx` 再按 `backing / 1290` 缩放，所以全部绘制代码的坐标一点不用改。
- 改 `cv.width/height` 会重置 context 全部状态（含 transform），所以每次 resize 后都重新 `setTransform`。
- 蒙层的椭圆在 78% 半径处已完全透明，左右两侧（排行条所在的 0~10% 与 90~100% 区域）不受影响。
- 结算信息本身靠 `text-shadow` + 中间暗池保证可读，不再需要全屏压暗。

### 57.5 验证

| 项 | 方法 | 结果 |
|---|---|---|
| 语法校验 | 13 个 js 逐个 `node --check` | ✅ 全过 |
| 后备存储 | 2499×1163 窗口下读 `cv.width` / `getBoundingClientRect()` | ✅ backing 1698×790 = CSS 尺寸 × DPR(1)，`ctx` scale 1.316，逻辑坐标仍是 1290×600 |

## 61. 修复：大狗在激光释放中阵亡会残留光束（同日第 61 次）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `js/30-sim.js` | `onUnitDeath()` 开头清空 `u.st.laserT / laserTick`（死亡立刻收回激光） |
| 2 | `js/30-sim.js` | `finish()` 里把**所有单位**的 `laserT` 归零：结算后 `tick` 停跑，否则光束会定格在结算画面上 |
| 3 | `js/40-render.js` | `drawLasers()` 增加 `!u.alive` 判断，渲染侧再兜一层 |

### 66.2 做法
